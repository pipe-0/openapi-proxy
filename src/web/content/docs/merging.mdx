---
title: Merging rules
description: What happens when a project is made of several OpenAPI documents, and two of them define the same thing.
---

A project can be assembled from several OpenAPI documents. Their operations are combined into one document, and variants select from the whole. [Several documents and audiences](/docs/several-documents) shows how to set that up. This page says what the merge does.

A merge runs by itself every time a document changes, so it cannot stop and ask. It follows fixed rules, and the project says what it did.

## The rules

**One document is the main one.** Its `info` and its `servers` describe the merged API. The servers of the other documents are not carried over, so the address of an internal service does not end up in a public document. In a file it is the source with `main: true`. In the app it is the one marked Main, and any document can be made the main one.

**Every operation keeps its security.** If a document sets a default `security` for all of its operations and the main document has a different one, that default is written onto each of its operations. A service that asks for an API key keeps asking for it, and a public one stays public.

**The same operation in two documents: the main one's is kept, then the earlier one's.** "The same" means the same method and path, where paths that differ only in a parameter's name count as the same (`/users/{id}` and `/users/{userId}`). The other operation is left out, and the project lists it. Two documents can each add methods to one path, as long as they describe the path itself the same way: the same spelling and the same path-level parameters.

**The same name for two different things: the later one is renamed.** If two documents both have a schema called `Error` and they are identical, including everything they reference, they become one. If they differ, the later document's becomes `BillingError`, named after that document, and every reference to it follows. Each operation keeps exactly the schema it had. The same goes for parameters, responses, security schemes and operation ids.

**Tags are combined by name.** An operation tagged `Users` in either document appears under `Users`.

## A path prefix

A service that is mounted under the main API usually describes its paths without the mount point: `/invoices`, not `/billing/invoices`. Give its document a `pathPrefix` and the prefix is put in front of every one of its paths.

## Documents in different OpenAPI versions

A 3.0 document can be merged with a 3.1 one. The two describe schemas in different dialects, so the 3.0 document is converted to 3.1 first, which loses nothing. The project says when that happened. See [URLs, formats and versions](/docs/urls#openapi-versions).

## What you see

- **In the app, on the project's documents:** each document with its status, and under them "What merging changed": operations left out, things renamed, servers not carried over.
- **In the editor:** operations that came from a document other than the main one are marked with its name, and typing that name in the filter finds them.
- **From the command line:** `openapi-proxy operations` lists the merged operations. An operation that was left out is not in the list.

If a followed document cannot be fetched, its last good copy stays in the merge and the others keep updating. The project shows which one failed and why.

## Limits

Up to 10 documents in a project, and 5 MB for all of them together.
