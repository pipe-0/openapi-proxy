An OpenAPI document is a map of a backend: every route, every field, every error. For a public API that is the point. For an internal one, or for the part a single partner integrates against, it is exactly what should not be readable by anyone who finds the URL.

So the document goes behind authentication, and the tools that used to read it stop working.

## What breaks

Most tools that consume OpenAPI take a URL and fetch it with a plain request. Mintlify's documentation [says so directly](https://www.mintlify.com/docs/help-center/openapi-url-fetch-fails-during-build): "Build fetches are unauthenticated and cannot send a token, cookie, or come from an allowlisted IP." Its advice for a document that needs authentication is to commit the file to the docs repository.

That is the usual outcome. The private document becomes a file in a repository, copied there by a person, and from then on the docs describe the API as it was on the day of the copy.

## Three ways to do it

**Commit a copy.** Simple, and stale by design. It works when someone owns the job of updating it and the API changes rarely.

**A URL nobody can guess.** A long random path instead of a credential. Any tool can read it, which is the appeal. The weakness is that the address is now the secret. It appears in CI logs, build configs and messages between colleagues, and the only way to take access away from one reader is to change it for all of them.

**A key, fetched in CI.** The document answers only to a credential. The pipeline that builds the docs or the SDK fetches it first and hands the tool a file:

```sh
curl -fsS https://proxy.example.com/v/acme/internal.json \
  -H "Authorization: Bearer $KEY" \
  -o openapi.json
```

This is the one that keeps both properties: the document stays private, and what gets built is the document as it is now. Some tools can send the header themselves; OpenAPI Generator, for one, has an `--auth` option for the fetch.

## What a private URL should do

If you put a credential in front of a document, a few details decide whether it stays pleasant to use.

- **One key per reader.** The docs build, the SDK pipeline and each partner get their own, so revoking one does not break the others.
- **Keys that only read.** A key that fetches a document should not be able to change anything.
- **Keys limited to one document.** A partner's key should open the partner's document and nothing else.
- **A clear answer without a key.** A `401` that says how to authenticate saves an afternoon of guessing.
- **Private caching.** `Cache-Control: private`, so no shared cache between you and the reader keeps a copy, and an `ETag` so a pipeline can still ask "anything new?" cheaply.

## In practice

In [openapi-proxy](/), every variant is public or private, and a workspace or a project can make private the default. A private variant is read with a user API key sent as `Authorization: Bearer`.

Next to a private variant's URL there is a button that creates a key for that variant alone. It is read-only and opens no other document, which makes it the key to hand to a partner or to store as a CI secret. A key can also read all of a workspace's private variants, for a pipeline that builds several.

The source can be private as well. The proxy fetches your backend's full document with request headers you give it, stored encrypted and sent only to that document's own origin. So the whole chain can be closed: a private source, and private variants of it for each reader. The URLs and status codes are in [Private variants and keys](/docs/private-variants).
