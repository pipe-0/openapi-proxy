The [Overlay Specification](https://spec.openapis.org/overlay/v1.0.0) reached version 1.0.0 in October 2024, and it has become a common answer to a common problem: one OpenAPI document as the source of truth, and several versions of it for different readers.

An overlay is a small document of its own. It lists actions, and each action points at part of an OpenAPI document with a JSONPath expression and either merges something into it or removes it:

```yaml
overlay: 1.0.0
info:
  title: Public view
  version: 1.0.0
actions:
  - target: $.paths.*[?@['x-internal'] == true]
    remove: true
  - target: $.info
    update:
      title: Acme API
```

Apply that to the full document and you get one without the operations marked `x-internal`, under a public title.

## What overlays do well

The idea behind them is sound, and worth keeping whatever tool you use. In the words of a [recent piece on overlays for several audiences](https://apievangelist.com/2026/07/06/openapi-overlays-for-filtering-multiple-audiences/): "The public copy should be an artifact you generate, not a file you edit."

Overlays are good at edits. Better descriptions than the framework generated, examples added by the docs team, a different `servers` list for a sandbox. These are changes someone wants to make on top of the source, and an overlay keeps them in a file that can be reviewed and applied again.

## What remove leaves behind

For deciding what an audience sees, there are two things to know.

**Remove deletes the node, and nothing else.** The specification defines `remove` as removing the target. It does not say anything about what the target referenced. Take out `POST /admin/impersonate` and the `StaffImpersonation` schema it used is still in `components`, with every field name. Redocly made this point when it [argued against overlays](https://redocly.com/blog/openapi-overlays): an overlay "would not remove any components that were referenced from the internal operations" and by nothing else. The other direction can go wrong too: remove a shared component and whatever still refers to it is left with a reference to nothing.

So an overlay that removes operations needs a second step that drops unused components, done by a tool, after the overlay ran.

**Removing is opt-out.** An overlay that removes internal operations publishes everything it does not mention. When the API gains an endpoint and nobody marks it, it is in the public document on the next run. For edits that default is harmless. For "what may the public see" it is the wrong way round.

## Selecting is a different operation

A filter starts from the other end. It says which operations a reader gets, and the rest follows:

- the components those operations reference are kept, to any depth, and all others are dropped
- tags and security schemes that nothing uses any more go with them
- an operation that appears later is not part of the selection until someone adds it

The two are not rivals. Deciding what an audience sees is a selection. Changing what the selected part says is an edit. A setup that uses each for its job is easier to reason about than an overlay that tries to do both.

## How openapi-proxy divides it

[openapi-proxy](/) does the selection. You check the tags or operations an audience gets, and the result is served at a URL, pruned to what those operations reference. Checking a whole tag keeps it as a rule, so the selection follows the API where you want it to and nowhere else.

For the edits people most often reach for an overlay to make, a variant has its own title, description and servers, which is how the same selection becomes a production and a sandbox document. See [A variant for each environment](/docs/several-documents#environments).

It does not apply overlay files. If you rewrite descriptions and examples with one, run it in the build that produces your source document, and let the proxy select from the result. Either way, the test from [the post on internal endpoints](/blog/public-openapi-document-without-internal-endpoints) applies: fetch your public document and count the schemas no remaining operation references. That number should be zero.
